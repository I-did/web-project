## Создание Pull Request

- PR открывается из рабочей ветки в `main`
- Прямой push в `main` запрещен
- Заголовок PR оформляется по Conventional Commits: `<type>(<region>): <short descr>`

## Как проходит ревью

### Автор

- Должен отвечать на все комментарии
- Должен вносить правки или аргументированно объяснять, почему правка не нужна.
- После правок снова запрашивать ревью.
- Не сливать PR до получения одобрения и зеленого CI.

### Ревьюер

- Должен дать первый ответ в течение одного рабочего дня
- Проверить:
  - соответствие PR задаче
  - корректность логики и обработку ошибок
  - наличие и качество тестов
  - читаемость и поддерживаемость кода
  - обновление документации, если требуется
- Не придираться к стилю, который проверяется линтерами
- Разделять комментарии на блокирующие и неблокирующие

### Префиксы комментариев

- `must:` - блокирующее замечание, без исправления PR нельзя одобрить
- `should:` - желательно исправить, не блокирует слияние
- `nit:` - мелочь, на усмотрение автора
- `question:` - вопрос, нужен ответ
- `suggestion:` - предложение

### Правила одобрения

- Для слияния требуется минимум 1 одобрение
- Автор не может одобрить сам себя
- Если после одобрения добавлены новые коммиты, то нужно проверить заново
- PR не может быть слит, пока есть неразрешенные блокирующие комментарии
- Если ревьюер недоступен, то обратиться к менеджеру проекта для назначения другого ревьюера

## Как проходит слияние

- Используем Squash merge
- Заголовок PR становится темой итогового коммита в `main` (поэтому, название PR в виде коммита)
- После merge рабочая ветка удаляется
