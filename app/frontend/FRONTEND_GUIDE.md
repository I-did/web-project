# Frontend MVP — «Форма»

Vue 3 + TypeScript + Pinia + Vue Router + Vite. Без внешнего UI-фреймворка: дизайн-токены и компоненты подготовлены к последующей адаптации под Figma/Tailwind.

## Маршруты

- `/` — лендинг
- `/payment` — создание заказа и CloudPayments (не работает без настроенного backend и public ID)
- `/activate?token=...` — принятие приглашения Directus
- `/login` — авторизация Directus
- `/questionnaire` — анкета с условными шагами
- `/dashboard` — кабинет с результатом отправленной в текущей сессии анкеты
- `/nutrition` — неделя питания (пока контракт `meal_plan` не согласован, отображается соответствующее сообщение)
- неизвестные URL — страница 404

## Запуск

```bash
cd app/frontend
npm ci
cp .env.example .env
npm run dev
npm run build
```

Установить `VITE_API_URL`, а для оплаты — `VITE_CLOUDPAYMENTS_PUBLIC_ID`.
Можно запустить **только предварительный просмотр интерфейса** с `VITE_PREVIEW_MODE=true`: снимается исключительно клиентское перенаправление на `/login`. Ни авторизация, ни данные, ни отправка анкеты на сервер не подменяются моками.

## Разделение ответственности

- `src/views` — композиция экранов, никаких вычислений КБЖУ
- `src/components/ui` — интерфейсные примитивы
- `src/components/layout` — каркас страницы
- `src/data/questionnaire.ts` — конфигурация шагов и чистая валидация
- `src/stores` — реактивное состояние и действия
- `src/services` — HTTP-граница, без секретов сервера

## Что ещё согласовать с командой

1. Формат ответа `/custom/calculate-nutrition` и `meal_plan` (сейчас выводится информация о несовпадении контракта вместо выдуманных блюд).
2. Серверное сохранение и повторная загрузка профиля/плана для авторизованного пользователя. Сейчас результат анкеты сохраняется в Pinia **только до обновления страницы**.
3. Отдельную ссылку приглашения Directus (может отличаться в установленной версии).
4. Коэффициенты активности: в требованиях 4 коэффициента, в форме 3 варианта. Фронтенд не рассчитывает КБЖУ, это делает сервер.
5. Правила обязательности пищевых ограничений и точный перечень категорий.
6. Тренировки, фото и дневник измерений — **post-MVP**, намеренно не добавлены как работающие функции.
7. Безопасность: доступ к коллекциям и проверка платежа обеспечиваются сервером; client-side guard не защита данных. Не храните service token / CloudPayments API secret в `VITE_*`.

## Границы готовности

Это работающий каркас фронтенда с реальными HTTP-вызовами, но без настроенного бэкенда покупки, авторизации и плана данные не будут сформированы. Продакшен-готовность требует полноценного refresh-token flow и защиты серверных ролей, а также интеграционных тестов.
