## Пользовательский путь и бизнес-логика

### Первый этап MVP

На первом этапе MVP будет реализовано:

1. Пользователь открывает страницу оплаты.
2. Указывает e-mail, ФИО, согласия, создается order со статусом pending_payment.
3. Оплачивает через CloudPayments.
4. CloudPayments присылает webhook, бэкенд проверяет подпись, переводит заказ в paid.
5. Менеджер видит оплаченный заказ, создает пользователя и отправляет ему данные для входа через одноразовую ссылку.
6. Пользователь активирует аккаунт, авторизуется и проходит анкету.
7. Расчет КБЖУ, формиируется план питания из заведенных в админку приемов пищи.

В следующих итерациях: подбор плана тренировок, ведение фото-прогресса и замеров, замена приема пищи и сброс анкеты.

### Оплата

На странице оплаты пользователь вводит ФИО и E-mail, нажимает кнопку оплатить, создается `order` и вызывается `CloudPayments Payment Widget`:

1. Vue -> POST `/custom/orders/create` { email, full_name }
2. Сервер (custom endpoint, service token):
  - валидирует email и ФИО;
  - генерирует `invoice_id` (UUID v4);
  - создает `orders` с `status = pending_payment`, `amount`, `email`;
  - возвращает { invoice_id, amount }.
3. Vue открывает виджет CloudPayments с invoiceId = invoice_id и amount / 100 (в рублях).
4. Виджет -> onSuccess -> Vue вызывает POST `/custom/orders/{invoice_id}/verify`.
5. Сервер проверяет оплату через CloudPayments API (GET /payments/find?invoiceId=... с Basic Auth) и, если оплата реально прошла, обновляет `orders: status = paid`, `cloudpayments_transaction_id`, `paid_at`, `payment_method`.

Пользователь на этом шаге еще не аутентифицирован, поэтому фронтенд не может писать в `/items/orders` напрямую, а только через кастомный эндпоинт с сервисным токеном.

### Жизненный цикл пользователя

Роль пользователя участника марафона: `Participant`.

Directus CMS предоставляет встроенный функционал для приглашения пользователей.

1. В админке есть кнопка Invite User. В теле передается email и role (UUID роли Participant).
2. Пользователь создается со статусом invited. В этом статусе он не может войти ни в приложение, ни в API, пока не примет приглашение и не задаст пароль.
3. Directus отправит письмо со ссылкой на активацию. Для этого будет подключен почтовый провайдер, например, SMTP в настройках проекта.
4. Когда пользователь переходит по ссылке и задает пароль, его статус автоматически меняется на active, и он получает доступ к API с правами роли Participant.
5. Когда марафон для пользователя завершен (4 недели прошли), то доступ сохраняется, но недели перестают меняться.

`invited` и `active` это встроенные статусы пользователей в Directus.

### Многошаговая анкета

Анкета многошаговая, будем хранить состояние только локально.
Для расчета суточной нормы КБЖУ будет использоваться формула Миффлина-Сан Жеора:

**Для мужчин:** BMR = 10 × масса (кг) + 6,25 × рост (см) − 5 × возраст (лет) + 5

**Для женщин:** BMR = 10 × масса (кг) + 6,25 × рост (см) − 5 × возраст (лет) − 161

| Шаг | Вопрос | Ветвление/условие |
|-----|--------|-------------------|
| 1   | Цель (снижение/поддержание/набор) | Задает коэффициент (0.8/1.0/1.1) |
| 2   | Пол | Мужской: формула Миффлина-Сан Жеора с +5; женский: с –161 |
| 3   | Параметры тела (вес, рост, возраст, желаемый вес) | Валидация: вес и желаемый вес в допустимом диапазоне, рост/возраст в разумных пределах; при некорректных значениях переход блокируется (БТ-02) |
| 4   | Признак грудного вскармливания | Только если пол = женский; при true -> к BMR прибавляется +500 ккал (БТ-03) |
| 5   | Стаж тренировок и активность | Задает коэффициент (1.2/1.375/1.55/1.725) |
| 6   | Пищевые ограничения (до 5 категорий) | UI блокирует выбор >5 (БТ-06); выбранные категории -> в фильтр _nin при подборе блюд |
| 7   | Исключения по /мясным/рыбным | Подкатегории уточняются и также попадают в фильтр (БТ-07) |
| 8   | Физические ограничения | Влияют на фильтр тренировок (БТ-08) |
| 9   | Место занятий (дом/зал) | Ветвление: если "дом" -> появляется шаг про инвентарь (БТ-09, БТ-10) |
| 10  | Инвентарь для дома | Только если место = "дом"; если "без инвентаря" -> фильтр по equipment = none |
| 11  | Проблемные зоны | Сохраняются в профиле, пока сущевстуют просто так |

### Финал анкеты

После последнего шага:

- Vue 3 собирает payload и отправляет POST /custom/calculate-nutrition (кастомный эндпоинт).
- Выполняется расчет КБЖУ.
- Выполняется подбор блюд и тренировок (запросы к коллекциям/таблицам).
- В базу данных сохраняется результат.
- Возвращается объект: bmr, tdee, target_calories, macros, meal_plan (28 завтраков, 28 обедов, 28 ужинов, 56 перекусов), workout_plan (4 недели).
- Доступен сброс анкеты (БТ-20) с очисткой профиля и возможностью пройти заново.

### Расчет КБЖУ

Формула: Миффлина-Сан Жеора.

- BMR:
  - мужчины: (10 × вес) + (6.25 × рост) – (5 × возраст) + 5
  - женщины: (10 × вес) + (6.25 × рост) – (5 × возраст) – 161
- Грудное вскармливание: BMR += 500 ккал.
- TDEE: BMR × коэффициент активности (1.2 / 1.375 / 1.55 / 1.725).
- Целевая калорийность: TDEE × 0.8 (снижение), × 1.0 (поддержание), × 1.1 (набор).
- БЖУ: 30% белки / 25% жиры / 45% углеводы; 1 г белка/углеводов = 4 ккал, 1 г жира = 9 ккал.
- Расчет только на бэкенде.

### Подбор плана питания

После расчета target_calories сервер формирует запрос к базе блюд. Пример распределения:

| Прием   |	Доля от target_calories |	Пример диапазона при 2000 ккал | Кол-во на 4 недели |
|---------|------|--------------|----|
| Завтрак |	~25% | 450–550 ккал | 28 |
| Обед    | ~30% | 550–650 ккал | 28 |
| Ужин    | ~25% | 450–550 ккал | 28 |
| Перекус | ~10% | каждый	180–220 ккал | 56 |

Фильтры запроса:

- calories between (min, max)
- category NOT IN (выбранные ограничения)
- limit: 28 (для завтраков/обедов/ужинов) или 56 (для перекусов).

Такой запрос напрямую выражается в стандартном API к бэкенду.

### Пример расчета: женщина, снижение веса, без молочных продуктов

#### Данные анкеты

| Параметр              | Значение |
|-----------------------|----------|
| Пол                   |	Женский  |
| Возраст               | 30 лет   |
| Вес                   | 70 кг    |
| Рост                  | 165 см   |
| Грудное вскармливание | Нет      |
| Активность            |	Легкая (1–3 тренировки в неделю) -> коэффициент 1.375 |
| Цель                  |	Снижение веса -> коэффициент 0.8 |
| Ограничения           | Категория "молочные продукты" |

#### Расчет КБЖУ

**BMR (Basal Metabolic Rate):**
```
(10 × 70) + (6.25 × 165) − (5 × 30) − 161
= 700 + 1031.25 − 150 − 161
= 1420.25 ккал
```

**TDEE (Total Daily Energy Expenditure):**
```
1420.25 × 1.375 = 1952.84 ккал
```

**Целевая калорийность (снижение веса):**
```
1952.84 × 0.8 = 1562.27 ккал ≈ 1562 ккал
```

**Распределение БЖУ (30/25/45):**

| Нутриент | %   | Калории | Граммы  |
|----------|-----|---------|---------|
| Белки    | 30% | 468.6   | 117.2 г |
| Жиры     | 25% | 390.6   | 43.4 г  |
| Углеводы | 45% | 702.9   | 175.7 г |

**Распределение калорий по приемам пищи:**

| Прием   | Доля | Целевой диапазон, ккал |
|---------|------|------------------------|
| Завтрак | ~25% | 360–420                |
| Обед    | ~30% | 440–500                |
| Ужин    | ~25% | 360–420                |
| Перекус | ~10% | 140–180                |

#### Пример API запроса для составления плана питания

Предполагаются коллекции:

- `dish_types`: завтрак, перекус 1, обед, перекус 2, ужин
- `dish_targets`: снижение веса, поддержание веса, набор веса
- `dish_categories`: категории приемов пищи (молочные продукты, мясо и т.д.)
- `dishes`: прием пищи с полем "калории" и связями с остальными коллекциями

```json
GET /items/dishes
  ?filter={
      "_and": [
        { "calories": { "_between": [360, 420] } },
        { "dish_types": { "dish_types_id": { "name": { "_eq": "Завтрак" } } } },
        { "dish_targets": { "dish_targets_id": { "name": { "_eq": "Снижение веса" } } } },
        { "dish_categories": { "_none": { "dish_categories_id": { "name": { "_eq": "Молочные" } } } } }
      ]
    }
  &limit=28
```

Полученные данные связываются с пользователем для отображения на страницах личного кабинета.

## Выбор архитектурной модели

**Монолит** - приложение собирается и деплоится как единое целое. Просто начать, но по мере роста код расплвается. Любое изменение требует понимания всего приложения.

**Модульный монолит** - тоже единый деплой, но внутри код разделен на модули. Его легче понимать и поддерживать.

**Микросервисы** - приложение разбито на независимые сервисы, которые могут деплоиться по отдельности. Общаются по сети. Дают независимое масштабирование и изоляцию отказов, но требуют инфраструктуры.

**Микроядро** - небольшое ядро + набор подключаемых модулей/плагинов. Хорошо работает, когда продукт должен расширяться третьими сторонами.

**Модульный монолит для нашего MVP подходит лучше всего. Он сохраняет единый деплой и простой локальный запуск. Так же, задает явные границы модулей (auth, questionnaire, nutrition, workouts, progress, shared), каждый из которых владеет своими данными и предоставляет публичный контракт.**

### Сравнительная таблица архитектурных подходов

| Критерий                           | Монолит     | Модульный монолит | Микросервисы | Микроядро |
|------------------------------------|-------------|-------------------|--------------|-----------|
| Сложность деплоя                   | Низкая      | Низкая            | Высокая      | Средняя   |
| Явные границы модулей              | Нет         | Да                | Да           | Да        |
| Скорость выхода MVP                | Высокая     | Высокая           | Низкая       | Средняя   |
| Подходит небольшой команде         | Да          | Да                | Нет          | Частично  |
| Операционная нагрузка              | Минимальная | Минимальная       | Высокая      | Средняя   |
| Независимое масштабирование частей | Нет         | Частично          | Да           | Частично  |
| Изоляция отказов                   | Нет         | Нет               | Да           | Частично  |
| Тестируемость бизнес-логики        | Средняя     | Высокая           | Высокая      | Средняя   |
| Эволюция к микросервисам           | Болезненная | Постепенная       | -            | Нет       |
