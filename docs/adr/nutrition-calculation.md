# Контракт API и архитектура модуля «Расчёт КБЖУ»

**Проект:** КБЖУ  
**Статус:** обновлённый проект контракта; коэффициенты активности и отображение чисел согласованы, остальные открытые решения перечислены в разделе 6  
**Путь API:** `POST /custom/calculate-nutrition`  
**Версия контракта:** 1.1 (предложение, 12.11.2026)

## 1. Цель и границы ответственности

Модуль **«Расчёт КБЖУ»** принимает проверенные параметры участника и выполняет детерминированный расчёт BMR, TDEE, целевой калорийности и макронутриентов.
Он **не запрашивает блюда**, не знает структуру коллекций `dishes`, `dish_types`, `dish_categories` и не формирует `meal_plan`.

`POST /custom/calculate-nutrition` — **операция верхнего уровня**, объединяющая независимые модули: 
(1) валидация анкеты, 
(2) расчёт КБЖУ, 
(3) сохранение расчёта, 
(4) отдельный вызов формирования плана питания, 
(5) ответ клиенту. 
Поэтому `meal_plan_id` присутствует в ответе **эндпоинта**, но не в результате чистой функции расчёта.

**MVP:** КБЖУ и 4-недельный план питания. Подбор тренировок, прогресс, фото и сброс анкеты относятся к последующим итерациям и не должны быть обязательными зависимостями расчёта.

## 2. Контракт HTTP

### 2.1. Запрос

| Параметр | Значение |
|---|---|
| Метод | `POST` |
| URL | `/custom/calculate-nutrition` |
| Авторизация | `Authorization: Bearer <access_token>` (роль `Participant`) |
| Заголовок | `Content-Type: application/json` |
| Тело | Объект `{ "answers": { ... } }` |
| Успех | `200 OK` (повторный расчёт по актуальной анкете — предложение; альтернативный `201 Created` требуется согласовать) |

```json
{
  "answers": {
    "goal": "weight-loss",
    "gender": "female",
    "breastfeeding_children": "n",
    "current_weight": 70,
    "desired_weight": 60,
    "height": 165,
    "age": 30,
    "training_experience": "middle",
    "daily_activity": "medium-active",
    "excluded_categories": ["molochnye-produkty"],
    "excluded_meat_products": [],
    "excluded_milk_products": ["all"],
    "excluded_fish_products": [],
    "training_restrictions": [],
    "training_place": "at-home",
    "home_inventory": ["with-weight"],
    "focus_body_parts": ["belly"]
  }
}
```

#### Поля и валидация

| Поле | Тип | Правило |
|---|---|---|
| `goal` | enum | Обязательно: `weight-loss`, `weight-maintaining`, `weight-gain` |
| `gender` | enum | Обязательно: `male`, `female` (варианты исходной анкеты) |
| `breastfeeding_children` | enum | `y`/`n` для `female`; для `male` отсутствует или `n`, значение `y` недопустимо |
| `current_weight`, `desired_weight` | number | Обязательно: 40–200 кг |
| `height` | number | Обязательно: 120–250 см |
| `age` | integer | Обязательно: 18–70 лет |
| `training_experience` | enum | `newbie`, `middle`, `expert`; в первом MVP может передаваться, но не входит в формулу |
| `daily_activity` | enum | Обязательно; `inactive`, `medium-active`, `high-active`; коэффициенты `1.2`, `1.375`, `1.725` соответственно |
| `excluded_categories` | string[] | 0–5 категорий, значения из справочника; исключения применяет **модуль питания** |
| `excluded_meat_products`, `excluded_milk_products`, `excluded_fish_products` | string[] | Передаются для выбранных родительских категорий; `all` не сочетается с отдельными подкатегориями |
| `training_restrictions`, `home_inventory`, `focus_body_parts` | string[] | Опциональные поля для будущих итераций; игнорируются расчётом КБЖУ |
| `training_place` | enum | Опционально для MVP: `at-home`, `in-gym`; `home_inventory` применим только для `at-home` |

**Примечание:** диапазоны взяты из JSON анкеты архитектурного описания; их пригодность для всех пользователей и безопасность формулы требуют согласования с предметным специалистом. Недопустимые комбинации параметров и неизвестные ключи необходимо обрабатывать единообразно; предложено неизвестные ключи отклонять с `400`.

### 2.2. Успешный ответ

Предлагаемая форма ответа (не оборачивать в `data`, если команда утверждает именно такой контракт):

```json
{
  "nutrition_calculation_id": 123,
  "bmr": 1420.25,
  "tdee": 1952.84375,
  "target_calories": 1562.275,
  "macros": {
    "protein_g": 117.170625,
    "fat_g": 43.39652777777778,
    "carbs_g": 175.7559375
  },
  "meal_plan_id": 456
}
```

- `nutrition_calculation_id`: ID записи `nutrition_calculations`, принадлежащей авторизованному участнику.
- `bmr`, `tdee`, `target_calories`: числовые значения килокалорий в сутки; сервер не округляет их ради отображения.
- `macros`: числовые значения граммов в сутки; сервер не округляет их ради отображения.
- `meal_plan_id`: ID созданного 4-недельного плана из отдельного модуля питания.
- В JSON передаются числа, не строки с запятыми или пробелами; фронтенд округляет/форматирует значения только при показе. Пример иллюстрирует вычисления, последняя цифра дроби при использовании IEEE 754 может немного отличаться. Точность хранения в БД требуется зафиксировать отдельно.
- Сервер не принимает `user_id` из тела: владелец определяется по авторизованной сессии.
- `meal_plan_id` обязателен **только при полном успехе** операции. Частичный результат оформляется ошибкой, а не успешным ответом с фиктивным ID.

### 2.3. Ошибки

Предлагается единая форма ошибок в стиле Directus (коды приложения утверждаются командой):

```json
{
  "errors": [
    {
      "message": "Вес должен быть в диапазоне от 40 до 200 кг",
      "extensions": {
        "code": "INVALID_PAYLOAD",
        "field": "answers.current_weight"
      }
    }
  ]
}
```

| HTTP | Код | Условие | Действие фронтенда |
|---|---|---|---|
| 400 | `INVALID_PAYLOAD` | Нет `answers`, неверный JSON, типы или значения, превышение 5 категорий, противоречащие ответы | Показать сообщение у поля; сохранить введённые данные |
| 401 | `UNAUTHORIZED` | Нет/истёк токен | Предложить повторный вход |
| 403 | `FORBIDDEN` | Аккаунт неактивен или нет разрешения на действие | Показать ошибку доступа |
| 409 | `CALCULATION_IN_PROGRESS` | Уже обрабатывается запрос для этого пользователя (если включена блокировка конкурирующих запросов) | Не отправлять дублирующие запросы, предложить повтор |
| 422 | `NOT_ENOUGH_DISHES` | КБЖУ рассчитано, но модуль питания не смог сформировать полный план с заданными исключениями | Объяснить причину, дать изменить ограничения; не показывать успешный `meal_plan_id` |
| 500 | `INTERNAL_ERROR` | Неожиданная ошибка вычисления/записи | Общее сообщение, журналирование технической причины |
| 503 | `DEPENDENCY_UNAVAILABLE` | Недоступна БД или сервис подбора плана | Предложить повторить позднее |

Коды `CALCULATION_IN_PROGRESS`, `NOT_ENOUGH_DISHES`, `DEPENDENCY_UNAVAILABLE` — **предлагаемые прикладные коды**, не утверждение о встроенных кодах Directus.
Точные коды и обработчики необходимо согласовать с backend-командой. Внутренние ошибки и стек вызовов клиенту не возвращать.

### 2.4. Повторный запрос и сохранение

- На фронтенде блокировать кнопку во время запроса; на сервере предусмотреть защиту от параллельных запросов одного пользователя.
- **Предлагаемая семантика:** одинаковый повторный запрос возвращает уже созданные результаты, а не плодит новые планы (идемпотентность).
- Реализация через `submission_hash`/ключ идемпотентности либо транзакционное ограничение; конкретный способ согласовать.
- При ошибке `NOT_ENOUGH_DISHES` не оставлять доступный пользователю «успешный» неполный план. 
- Если модули используют одну PostgreSQL БД, возможна общая транзакция на уровне Application Service; иначе — явная компенсация/статус операции. 
- Чистая функция расчёта от этого не зависит.
- Ответ всегда возвращается **после** успешного сохранения обоих ID.

## 3. Алгоритм расчёта (доменный модуль)

Используется формула Миффлина — Сан Жеора из архитектурного описания:

- Для `male`: `BMR = 10 × weight + 6.25 × height − 5 × age + 5`.
- Для `female`: `BMR = 10 × weight + 6.25 × height − 5 × age − 161`.
- При `breastfeeding_children = "y"`: `BMR += 500` ккал (**правило проекта**, не универсальная медицинская рекомендация).
- `TDEE = BMR × activityFactor`.
- `targetCalories = TDEE × goalFactor`, где `weight-loss` — `0.8`, `weight-maintaining` — `1.0`, `weight-gain` — `1.1`.
- Белки: `targetCalories × 0.30 / 4`; жиры: `targetCalories × 0.25 / 9`; углеводы: `targetCalories × 0.45 / 4`.

**Согласованная таблица активности (3 уровня):**

| `daily_activity` | Уровень | Коэффициент |
|---|---|---:|
| `inactive` | Низкая активность | `1.2` |
| `medium-active` | Средняя активность | `1.375` |
| `high-active` | Высокая активность | `1.725` |

Коэффициент `1.55` в текущую модель анкеты **не входит**. `training_experience` не используется при определении TDEE.

**Согласованное правило отображения:** расчётный модуль работает с числовыми значениями без принудительного округления по правилам интерфейса; в HTTP-ответе передаёт числа, а не форматированные строки. Фронтенд самостоятельно решает, как отображать значения (например, калории без знаков после запятой, БЖУ с одним знаком), не меняя исходные данные расчёта. Макросы рассчитываются из неокруглённой целевой калорийности. Допустимые погрешности вычисления `number` и точность полей PostgreSQL нужно определить при реализации.

**Контрольный пример для `medium-active`:** `BMR = 1420.25`; `TDEE = 1420.25 × 1.375 = 1952.84375`; `targetCalories = 1952.84375 × 0.8 = 1562.275`; белки `117.170625` г; жиры `43.396527777...` г; углеводы `175.7559375` г. На фронтенде эти числа могут отображаться в более удобном виде, но в API не вводится отдельное правило округления до 2/1 знаков.

## 4. Выбор GoF-паттерна

**Основной паттерн — Strategy.** Он отделяет различные алгоритмы расчёта от HTTP, Directus и планов питания. 
В MVP достаточно двух стратегий BMR (`MaleBmrStrategy`, `FemaleBmrStrategy`) или одной стратегии Миффлина — Сан Жеора с параметром пола; 
отдельные классы полезны только если действительно предполагаются разные алгоритмы. 
Для учебного проекта рекомендуемая реализация — один `MifflinStJeorStrategy` с чистым методом `calculate(input)` и таблицами коэффициентов,
а интерфейс позволяет позднее подменить формулу.

**Factory** — вспомогательный паттерн: выбирает реализацию `NutritionStrategy` по версии алгоритма (например, `mifflin-v1`) и конфигурации. 
Не использовать Factory для выполнения математических вычислений. 
Если пока одна реализация, достаточно простой функции `createNutritionStrategy()` — не создавать лишние абстракции.

**Application Service** — не GoF, а слой координации операции, который вызывает независимые модули.

```text
HTTP Controller (Directus endpoint)
  -> ValidateQuestionnaire
  -> CalculateNutritionUseCase (Application Service)
     -> NutritionStrategy (чистый расчёт)
     -> NutritionCalculationRepository (сохранение)
     -> MealPlanPort.createPlan({ userId, targetCalories, macros, exclusions })
        [реализуется модулем «План питания»]
  -> HTTP response { nutrition_calculation_id, ..., meal_plan_id }
```

### 4.1. Интерфейсы на TypeScript (псевдокод-контракт)

```ts
export interface CalculationInput {
  gender: 'male' | 'female';
  breastfeeding: boolean;
  currentWeightKg: number;
  heightCm: number;
  ageYears: number;
  activityFactor: number;
  goalFactor: number;
}

export interface CalculationResult {
  bmr: number;
  tdee: number;
  targetCalories: number;
  macros: { proteinG: number; fatG: number; carbsG: number };
}

export interface NutritionStrategy {
  calculate(input: CalculationInput): CalculationResult;
}

export interface NutritionCalculationRepository {
  save(userId: string, result: CalculationResult): Promise<number>;
}

// Порт другого модуля; расчётная стратегия о нём не знает.
export interface MealPlanPort {
  createPlan(input: {
    userId: string;
    targetCalories: number;
    macros: CalculationResult['macros'];
    excludedCategories: string[];
    excludedSubcategories: string[];
  }): Promise<{ mealPlanId: number }>;
}
```

## 5. Обязательные тесты

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| UNIT-01 | Контрольные женские параметры из примера | BMR `1420.25`, TDEE `1952.84375`, цель `1562.275` до округления |
| UNIT-02 | Мужская формула | Используется `+5`, а не `−161` |
| UNIT-03 | Грудное вскармливание `y` | Прибавка `500` по принятому правилу проекта |
| UNIT-04 | Цель: снижение/поддержание/набор | Коэффициенты `0.8` / `1.0` / `1.1` |
| UNIT-05 | Активность | `inactive` → `1.2`, `medium-active` → `1.375`, `high-active` → `1.725`; значение `1.55` не используется |
| UNIT-06 | Точность вычислений | Бэкенд не округляет для отображения; сравнение чисел с допустимой погрешностью, форматирование проверяется отдельно на фронтенде |
| UNIT-07 | Изолированность | Стратегия работает без Directus, HTTP, справочников блюд и базы данных |
| API-01 | Корректный токен + корректный payload | `200`, все поля, оба сохранённых ID |
| API-02 | Нет токена / чужой аккаунт | `401` / `403`, данные не раскрыты |
| API-03 | Вес ниже 40 или выше 200, возраст вне диапазона | `400 INVALID_PAYLOAD`, указано проблемное поле |
| API-04 | Более пяти категорий или конфликт `all` с подкатегорией | `400 INVALID_PAYLOAD` |
| API-05 | Недостаточно подходящих блюд | `422 NOT_ENOUGH_DISHES`, неполный план не выдаётся как успешный |
| API-06 | Повтор одного запроса | Нет дубликатов плана после утверждения способа идемпотентности |
| API-07 | Сбой сохранения/модуля питания | `500` или `503`, без утечки внутренней ошибки |

## 6. Вопросы на утверждение

**Уже согласовано:** три уровня активности с коэффициентами `1.2 / 1.375 / 1.725` и округление только при отображении на фронтенде.

1. Утвердить формат успеха (`200` при повторе или `201` при создании) и механизм идемпотентности.
2. Утвердить точность хранения чисел в PostgreSQL, без обязательного округления на API; задать допуск в unit-тестах.
3. Подтвердить обязательность полей тренировок в MVP и разрешённость пустых массивов исключений.
4. Подтвердить поведение при нехватке подходящих блюд: `422 NOT_ENOUGH_DISHES` либо другой согласованный сценарий.
5. Утвердить атомарность/компенсацию сохранения расчёта и плана, а также названия и поля коллекций в актуальном snapshot.
6. Подтвердить, нужен ли отдельный endpoint только для расчёта или достаточно изолированного доменного модуля внутри составного endpoint.
7. Проверить с командой бизнес-правила по целевым коэффициентам, грудному вскармливанию и распределению БЖУ; приведённые формулы являются условиями проекта, не универсальной медицинской рекомендацией.

---

**Итог:** HTTP endpoint составляет одну пользовательскую операцию, а чистая Strategy выполняет только математику. 
Factory выбирает реализацию, Repository сохраняет результат, модуль питания формирует рацион через отдельный порт. 
Так изменения рецептов и базы блюд не затрагивают расчёт КБЖУ.
