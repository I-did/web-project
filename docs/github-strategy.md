# Стратегия ветвления

## Общее

Решено использовать Feature Branch стратегию:

- Ветка main защищена, пушить в нее запрещено
- Любая работа выполняется в отдельной короткоживущей ветке
- Любое изменение в main только через Pull Request
- История main должна быть линейной, используем Squash/Rebase
- Pull Request не может быть слит без успешных првоерок CI, проверок линтеров и одного одобрения

## Ветки

`main` - стабильная ветка, состояние прода

| Префикс  | Использование              | Пример                    |
|----------|----------------------------|---------------------------|
| feature/ | Новый функционал           | feature/auth              |
| fix/     | Исправление бага           | fix/auth-error            |
| hotfix/  | Срочное исправление бага   | hotfix/payment-error      |
| chore/   | Инфраструктура репозитория | chore/update-vite-scripts |
| docs/    | Документаия                | docs/github-strategy      |

Лучше именовать ветку с ID задачи, например: `<type>/<task-id>-<краткое-описание>`

### Правила для рабочих веток

- одна ветка - одна задача или один логически связанный набор изменений
- ветка должна жить как можно меньше, чтобы между ней и main был наименьший разрыв
- нельзя пушить в main напрямую
- force push разрешен только в свою рабочую ветку и то через --force-with-lease
- после слияния Pull Request, ветка удаляется

## Коммиты

Формат коммитов по [Conventionial Commits](https://www.conventionalcommits.org/):

`<type>(<region>): <short descr>`

Допустимые type:

- feat - новая функциональность
- fix - исправление бага
- docs - документация
- style - форматирование без изменения логики
- refactor - рефакторинг без изменения поведения
- test - тесты
- chore - инфраструктура репозитория
- perf - оптимизация
- build - сборка
- ci - CI/CD

## Pull Request

### Как создавать

- PR создается после завершения работы над задачей
- PR всегда из рабочей ветки в main
- Нельзя создавать PR из main
- Нельзя смешивать в одном PR разные задачи

### Шаблон Pull Request

```markdown
## Что сделано
Кратко: какие изменения внесены

## Зачем
Ссылка на задачу и причина изменения

## Чек-лист
- [ ] ветка создана от `main`
- [ ] заголовок PR соответствует Conventional Commits
- [ ] линтеры и тесты проходят локально
- [ ] CI зеленый
- [ ] нет лишних файлов
- [ ] документация обновлена, если нужно
- [ ] добавлены/обновлены тесты, если нужно
- [ ] обсуждения в PR разрешены
```

## Ревью и слияние

- нужно назначить одного ревьюера из команды
- ревьюер все проверяет, вносит комментарии
- автор вносит правки, отвечает
- после устранения замечаний, ревьюер одобряет PR
- если после одобрения были добавлены новые коммиты, то одобрение сбрасывается
- выбран способ слияния Squash merge
- после слияния ветка удаляется
